## 进度偏慢的原因与责任

1. 推进单位过小：多轮集中在按钮、回执和单条测试，频繁结束与重启上下文，用户可见的完整体验增长慢。局部测试必要，但不应成为迭代交付单位。
2. 关键路径顺序不合理：G0 原生语音/搜索/实际播放尚未验证就持续向后展开，关键风险拖到后面；配置依赖影响真实验收，但不能成为本地集成推进慢的全部解释。
3. 早期界面与原型未先对齐造成返工；后续又逐控件修补，缺少一次完整同尺寸视觉和交互闭环检查。
4. 自动化通过与阶段完成分开说明了，但汇报仍过度强调新增测试数；对“用户现在能完整做什么”呈现不足。334 项通过不能代替 41 项功能验收。
5. 部分状态文档滞后，旧报告仍写主会话/导出缺失；缺少统一的当前缺口清单，导致上下文切换与优先级漂移。此表作为本次当前状态，旧报告保留为历史。
6. GitHub 网络失败影响远端备份；数据隔离、版本控制和安全回执本身是必要要求，不能通过省掉它们提速。主要调整应发生在组织与验证顺序。
